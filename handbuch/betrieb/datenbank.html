    Datenbank¶

    PostgreSQL ist die einzige Wahrheit einer Installation: Dokumente, Chunks samt Vektoren, Volltext, Metadaten, Konten, Rechte, Chats und Protokolle liegen in einer Datenbank. Daneben steht nur die Originalablage. Dieses Kapitel beschreibt, was eine Datenbank für OPAA mitbringen muss; wie sie im Compose-Stapel läuft, steht unter Docker Compose, wie sie gesichert wird, unter Sicherung und Wiederherstellung.

    Vektorspeicher: pgvector¶

    OPAA speichert Vektoren in PostgreSQL mit der Erweiterung pgvector; das ist der einzige unterstützte Vektorspeicher, ein Wechsel ist nicht vorgesehen. Metadaten und Vektorindex liegen damit in derselben Datenbank: ein Sicherungslauf, eine Wiederherstellung, ein Nachweispfad. Bekannte Grenze: pgvector stößt bei sehr großen Beständen im Bereich von Millionen Vektoren an Grenzen.

    • pgvector 0.8.0 oder neuer. Das Image pgvector/pgvector:pg18 bringt eine passende Fassung mit; bei einer älteren Erweiterung bricht der Start mit einer Meldung ab. Wer die Datenbank selbst betreibt und pgvector aktualisiert, führt danach ALTER EXTENSION vector UPDATE; aus.
    • Die Vektortabelle legt nicht die Migration an, sondern der Abschluss der Installation, mit der Dimension, die die Probeeinbettung des Embedding-Modells ergibt. Eine bestehende Installation behält ihre Vektortabelle. Nach einem Wechsel des Embedding-Modells stellt die Neueinbettung sie auf die neue Dimension um (Modelle); bis dahin stehen alte und neue Vektoren nebeneinander, und den Platz der alten gibt PostgreSQL erst frei, wenn die Zeilen neu geschrieben werden.
    • Die Distanzfunktion (OPAA_PGVECTOR_DISTANCE_TYPE) bestimmt, wofür der Vektorindex beim Anlegen der Vektortabelle gebaut wird. Passt der Wert später nicht mehr zum bestehenden Index, bricht der Start mit einer Meldung ab, die beide Werte und den Namen des Index nennt: Die Suche würde den Index sonst nicht mehr nutzen. Siehe „Distanzfunktion ändern“.
    • Eine neue PostgreSQL-Hauptversion (etwa ein Image-Tag pg18 → höher) ist ein eigener Migrationsvorgang der Datenbank mit Sicherung und Wiederherstellung, kein Image-Update: Das Datenverzeichnis ist nicht aufwärtskompatibel.

    Distanzfunktion ändern¶

    Der einfachste Weg nach dem Abbruch ist, den alten Wert von OPAA_PGVECTOR_DISTANCE_TYPE wieder einzutragen. Soll die neue Distanzfunktion gelten, wird der Index in der Datenbank neu gebaut, bei gestopptem Backend, mit dem Indexnamen aus der Meldung und der Operator-Klasse der neuen Distanzfunktion (vector_cosine_ops für cosine_distance, vector_l2_ops für euclidean_distance, vector_ip_ops für negative_inner_product):

    DROP INDEX CONCURRENTLY <schema>.<index>;
CREATE INDEX CONCURRENTLY <index> ON <schema>.vector_store USING hnsw (embedding vector_cosine_ops);
    • Immer mit CONCURRENTLY. Ohne den Zusatz sperrt der Neuaufbau eines HNSW-Index die Schreibzugriffe auf die Tabelle, bei großen Beständen lange. Mit dem Zusatz dauert er länger, sperrt aber nicht; die beiden Befehle laufen außerhalb einer Transaktion.
    • Während einer Neueinbettung nach einem Wechsel des Embedding-Modells (Modelle) gibt es einen zweiten Index, embedding_next_vector_index auf der Spalte embedding_next. Er kann ebenso betroffen sein und wird auf dieselbe Weise neu gebaut, mit embedding_next statt embedding. Die Meldung nennt je Start einen Index; passt danach ein weiterer nicht, nennt ihn der nächste Start.
    • Den Index nur zu löschen beseitigt den Abbruch, aber nicht das Problem: Ohne Index liest jede Suche still die ganze Tabelle, auch wenn alle Antworten weiter stimmen.

    Voraussetzungen einer eigenen PostgreSQL¶

    Der mitgelieferte Compose-Stapel startet PostgreSQL mit einem Superuser-Konto; dort ist nichts vorzubereiten. Eine Datenbank des Rechenzentrums stellt OPAA dagegen meist ein Konto ohne Superuser-Rechte zur Verfügung. Die Schemamigration braucht dann zwei Dinge, die ein Datenbankverwalter vor dem ersten Start einmalig anlegt:

    -- in der Datenbank von OPAA, als Superuser:
CREATE EXTENSION vector;
-- nur, wenn das Konto von OPAA nicht CREATEROLE hat:
CREATE ROLE opaa_audit_owner NOLOGIN;
GRANT opaa_audit_owner TO opaa WITH ADMIN OPTION;
    • Erweiterung vector (pgvector 0.8.0 oder neuer). Sie muss auf dem Datenbankserver installiert sein, etwa über das Image pgvector/pgvector oder das Paket postgresql-<Version>-pgvector. Anlegen darf sie ein Superuser; verwaltete Dienste (etwa Amazon RDS, Azure Database for PostgreSQL, Google Cloud SQL) erlauben es auch ihrer eigenen Verwaltungsrolle.
    • Rolle opaa_audit_owner. Ihr gehören die Protokolltabellen, damit das Konto von OPAA sie nicht löschen kann. Hat das Konto CREATEROLE, legt die Migration die Rolle selbst an. Eine vorab angelegte Rolle braucht WITH ADMIN OPTION, sonst scheitert die Migration mit permission denied to grant role.

    Daneben muss das Konto in der Datenbank Objekte anlegen dürfen, am einfachsten als Eigentümer der Datenbank. Für ein eigenes Schema gelten die Regeln im folgenden Abschnitt.

    Neben dem Connection Pool hält jede Instanz eine weitere, dauerhafte Verbindung (Anwendungsname opaa-invalidation-bus). Über sie erfährt sie Änderungen an Rechten, Anmeldeanbietern und Einstellungen sofort, auch wenn eine andere Instanz sie vorgenommen hat. Sie braucht eine direkte Verbindung oder einen Verbindungs-Proxy im Sitzungsmodus; im Transaktionsmodus (etwa PgBouncer mit pool_mode = transaction) kommt sie nicht zustande. OPAA liest Rechte und Einstellungen dann bei jeder Anfrage aus der Datenbank und meldet im Protokoll The invalidation bus does not listen. Die Verbindung zählt bei max_connections mit.

    Fehlt ein Recht, bricht die Migration mit der Meldung von PostgreSQL ab, etwa permission denied to create extension "vector". Ist pgvector auf dem Server gar nicht installiert, prüft OPAA das vor der Migration und bricht mit einem eigenen Bericht ab, weil die Meldung von PostgreSQL in diesem Fall verloren ginge:

        APPLICATION FAILED TO START

    Description:
    The PostgreSQL server has the pgvector extension not installed; the schema migration of OPAA needs it (CREATE EXTENSION vector).

    Action:
    Install pgvector 0.8.0 or later on the database server - e.g. the image pgvector/pgvector or the package postgresql-<version>-pgvector - and start OPAA again. See docs/handbuch/betrieb/datenbank.md, section "Voraussetzungen einer eigenen PostgreSQL".

    Eigenes Datenbankschema¶

    Ohne weitere Angabe legt OPAA alles im Schema public an. Mit OPAA_DB_SCHEMA lässt sich ein anderes Schema wählen, etwa um OPAA neben anderen Anwendungen in einer gemeinsam genutzten Datenbank zu betreiben. Das Backend setzt dann den search_path jeder Verbindung auf <schema>, public; Migrationen, Tabellen der Anwendung, die Vektortabelle und die Verwaltungstabelle der Migrationen landen im gewählten Schema. public bleibt nur als Rückfall im Suchpfad, damit eine dort bereits installierte Erweiterung vector auffindbar bleibt.

    Voraussetzungen:

    • Das Schema muss vor dem ersten Start existieren. Fehlt es, bricht die Migration beim Start ab, statt stillschweigend in public anzulegen.
    • Empfohlen: Das Schema gehört einer Verwaltungsrolle, und das Konto von OPAA erhält nur USAGE und CREATE, und zwar mit Weitergaberecht. Die Migration braucht dieses Recht, um es an die Eigentümerrolle der Protokolltabellen (opaa_audit_owner) weiterzugeben:
    CREATE SCHEMA opaa AUTHORIZATION dba;
GRANT USAGE, CREATE ON SCHEMA opaa TO opaa WITH GRANT OPTION;

    Gehört das Schema stattdessen dem Konto von OPAA (CREATE SCHEMA opaa AUTHORIZATION opaa), läuft die Anwendung ebenso. Das Konto darf dann aber als Schema-Eigentümer auch die Tabellen von opaa_audit_owner löschen, und der Löschschutz des Protokolls entfällt. Dasselbe gilt in public, wenn das Konto Eigentümer der Datenbank ist.

    • Das Schema wird vor der Erstinstallation festgelegt. Ein späterer Wechsel verschiebt keine Daten; die Installation im neuen Schema beginnt leer.
    • Die Rolle opaa_audit_owner (Eigentümerin der Protokolltabellen) gilt für die ganze PostgreSQL-Instanz. Eine zweite OPAA-Installation in derselben Instanz, aber mit anderem Konto, startet nicht: Ihre Migration darf die bestehende Rolle nicht vergeben (permission denied to grant role). Mit demselben Konto startet sie, kann dann aber das Protokoll der anderen Installation verändern. Getrennte Installationen gehören deshalb in getrennte PostgreSQL-Instanzen.
    • Die psql-Beispiele dieses Handbuchs lösen Tabellen über den Standard-Suchpfad auf. Bei einem eigenen Schema wird es vorangestellt, etwa PGOPTIONS='-c search_path=opaa' psql ….

    Migration als eigener Schritt¶

    Ohne weitere Angabe migriert jede Instanz die Datenbank beim Start, bevor sie Anfragen annimmt; Docker Compose und das Helm-Chart arbeiten mit einer Instanz so. Mit mehreren Instanzen trennen beide die Migration vom Start der Instanzen, damit kein Instanzstart eine Migration abbricht: der Dienst backend-migrate der Mehrinstanz-Variante (Docker Compose) und der Migrations-Job des Charts (Kubernetes). Von Hand:

    1. Das Backend-Image einmal mit OPAA_MODE=migrate und denselben Datenbankwerten starten. Es wendet die Migrationen an, legt die Vektortabelle an und endet mit Exit-Code 0. Jeder andere Exit-Code heißt: Die Migration ist gescheitert, die Instanzen bleiben auf dem alten Stand.
    2. Die Instanzen mit SPRING_FLYWAY_ENABLED=false starten. Sie migrieren nicht und warten nicht auf die Sperre der Migration.

    Wer die Reihenfolge nicht selbst abwarten kann, stellt jeder Instanz das Backend-Image mit OPAA_MODE=await-migration voran, wie es der Chart als Init-Container tut. Es liest nur, wartet, bis die Datenbank jede Migration seiner Version enthält, und endet dann mit Exit-Code 0; bis dahin nennt es im Protokoll alle 5 s, wie viele Migrationen noch fehlen. Ist die Datenbank nicht erreichbar, wartet es weiter.

    Eine Migration wartet höchstens fünf Sekunden auf die Sperre einer Tabelle und bricht dann ab, statt die Anfragen aller Instanzen hinter sich aufzustauen; der abgebrochene Lauf lässt sich wiederholen. Mehrere Instanzen, die gleichzeitig starten, wenden eine Antwortdatei nacheinander an und schließen die Installation genau einmal ab, nie doppelt.

    Update auf v0.1.0: Von einem Vorabstand (v0.1.0-rc.1 bis rc.4) aus ist es kein Rolling Update. Vorher alle Instanzen anhalten; die Migrationen dieser Stände entfernen Spalten und Tabellen, die eine noch laufende ältere Instanz braucht.

    Verbindungen bei mehreren Instanzen¶

    Jede Instanz öffnet bis zu OPAA_DB_POOL_SIZE Verbindungen in ihrem Pool und dazu eine dauerhafte Verbindung, über die sie Änderungen der anderen Instanzen erfährt. Der Migrationsschritt braucht zwei. PostgreSQL muss also für

    (Instanzen + 1) × (OPAA_DB_POOL_SIZE + 1) + 2

    Verbindungen Platz haben, zusätzlich zu allem anderen auf demselben Server. Die 1 neben den Instanzen ist die, die ein Rolling Update startet, bevor es eine alte beendet.

    Mehr öffnet eine Instanz auch unter Last nicht: Sind alle Verbindungen ihres Pools belegt, warten weitere Anfragen auf eine freie, höchstens 30 Sekunden, und enden danach mit einem Fehler. Wie viele Verbindungen eine Instanz wirklich hält, zeigt pg_stat_activity, gruppiert nach client_addr.

    Volltextsuche (lexikalischer Suchpfad)¶

    Neben der Vektorsuche läuft eine klassische Volltextsuche direkt in PostgreSQL, mit der german-Konfiguration und einem GIN-Index. Es gibt kein zweites System: derselbe Sicherungslauf, dieselbe Wiederherstellung, derselbe Verschlüsselungsnachweis. Der Pfad findet, woran eine Vektorsuche strukturell scheitert — Paragrafenverweise, Aktenzeichen, Erlassnummern, seltene Fachbegriffe. Wie seine Treffer mit denen der Vektorsuche zusammengeführt werden, steht im Kapitel Suche; scheitert die Volltextabfrage, scheitert die Frage, statt still eine halbe Suche zu liefern.

    Was zu tun ist¶

    Im laufenden Betrieb nichts. Jeder Chunk bekommt seinen Volltexteintrag in derselben Transaktion wie seinen Vektor.

    Ändert ein Update die Bildung des Volltextindex, liegen die betroffenen Einträge in einer älteren Fassung, und die Seite „Suche & Indexierung" weist die Bibliotheken mit Nachzug ausstehend aus. Der Pfad findet diese Einträge weiter, ihnen fehlen nur die Lexeme der neuen Fassung. Nachgezogen wird über den Pipeline-Nachzug (POST /api/v1/admin/indexing/pipeline-reindex, eine Oberfläche dafür gibt es noch nicht); er erfasst solche Abschnitte auch dann, wenn sich an der Aufbereitung des Dokuments sonst nichts geändert hat. Ein Update, das ihn nötig macht, nennen die Notizen des Release.

    Was das kostet: Der Nachzug liest jedes betroffene Dokument neu ein, zerlegt es und bettet es neu ein — in derselben Größenordnung teuer wie eine Neuindizierung dieser Dokumente. Er läuft stapelweise, ist unterbrechbar und wiederaufnehmbar; bis er durch ist, sucht der Pfad mit den Lexemen der alten Fassung.

    Bekannte Grenze: ts_rank ist kein BM25¶

    PostgreSQL bewertet Volltexttreffer mit ts_rank. Das ist nicht das BM25-Verfahren, das spezialisierte Suchmaschinen verwenden, und der Unterschied ist im Betrieb spürbar:

    • Keine Normalisierung auf die Textlänge. Lange Abschnitte werden systematisch überbewertet.
    • Keine Gewichtung nach Seltenheit. Ein Wort, das in fünf von 50 000 Abschnitten vorkommt, zählt kaum mehr als eines, das überall steht. Bei einem Bestand aus vielen ähnlich formulierten Satzungen ist genau das die schwache Stelle.

    Diese Grenze ist bewusst in Kauf genommen, aus zwei Gründen. Erstens braucht die Ergebnis-Fusion keine richtige Bewertung, sondern nur eine brauchbare Reihenfolge — eine deutlich schwächere Anforderung. Zweitens wird die Schwäche dort, wo der Pfad seinen Zweck erfüllt, kaum wirksam: Bei einer exakten Kennung ist der richtige Abschnitt meist der einzige, der die Zeichenfolge überhaupt enthält.

    Gegen den zweiten Punkt ist zusätzlich vorgesorgt: Paragrafenverweise, Aktenzeichen, Dienstanweisungs- und Formularnummern sowie Erlass- und Drucksachennummern werden zusätzlich als unzerlegte Kennungen geführt und höher gewichtet als Fließtext. Ohne das gewönne ein Abschnitt, der die Wörter der Frage nur oft genug wiederholt, gegen den einen Abschnitt, der die gesuchte Kennung tatsächlich führt — genau die Schwäche von ts_rank. Dabei ist gleichgültig, ob das Dokument die Kennung hinter einem Schlüsselwort nennt („mit dem Aktenzeichen BAU-DA-2/2024") und die Frage sie nackt („Was regelt die Dienstanweisung BAU-DA-2/2024?") — beide Schreibweisen führen auf dieselbe Kennung.

    Wann diese Grenze relevant wird: Wenn Fragen mit exakten Kennungen die falsche Fundstelle liefern, ist sie der erste Verdacht. Ob der Wechsel auf eine echte BM25-Erweiterung nötig ist, wird gemessen und nicht vermutet. Die festgelegte Eintrittsbedingung: Die Fallgruppen „Kompositum" und „exakte Kennung" des Suchqualitäts-Benchmarks bleiben — mit aktivem Kennungsschutz und aktivem Reranker — je einzeln unter Hit Rate@5 = 0,80, obwohl der Vektorpfad die betreffenden Kandidaten im gemessenen Fenster zeigt. Erst dann ist eine BM25-Erweiterung im selben PostgreSQL (eigenes Datenbank-Image) der nächste Schritt; eine externe Suchengine neben PostgreSQL bleibt die letzte Stufe, weil sie den Rechtefilter verdoppelt.

    Keine Kompositazerlegung. „Genehmigung" findet „Baugenehmigungsverfahren" im Volltextpfad nicht. Auch das ist eine bewusste Festlegung: Eine Zerlegung, die „Gebührenordnung" in „Gebühr" und „Ordnung" auflöst, verwässert auch Treffer. Ob sich der Tausch lohnt, entscheidet eine Messung, keine Vermutung.
